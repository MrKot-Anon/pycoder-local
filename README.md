# PyCoder

Самостоятельный терминальный кодер-агент на **Python 3.11+** с интерфейсом Textual.
Ядро использует стандартную библиотеку; зависимости интерфейса включены в сборку.
Цикл работы, сжатие контекста и алгоритм патчей адаптированы
из исходников Codex, ревизия `18344a972d`. Rust-бинарник Codex не используется.

## Локальная модель и MiniMax M2.5

```bash
./pycoder --локал                      # 127.0.0.1:8080
./pycoder --локал model-host.example:8080  # замените адресом своего сервера
./pycoder --local model-host.example       # тот же режим; порт по умолчанию 8080
./pycoder --локал -- "Проверь проект"   # -- отделяет задачу от необязательного адреса
```

Из исходников: `python3 run.py --локал model-host.example:8080`.
Поддерживаются `host`, `host:port`, IPv6 в квадратных скобках и полный HTTP(S) URL,
в том числе с `/v1` или `/v1/chat/completions`. У полного URL используется указанный
порт либо стандартный порт HTTP/HTTPS.

Режим подключается напрямую, игнорирует сохранённые SOCKS-прокси и не отправляет
API-ключи из окружения или файла. Модель автоматически определяется через
`/v1/models`; если их несколько, нужен `--model ID`. Явный `--model` позволяет
работать и с сервером без каталога. Контекст берётся из каталога, включая
`meta.n_ctx` у llama.cpp; без этих данных используется 32768. Начальный лимит
ответа — 4096 токенов, включая reasoning. Сохранённый вручную лимит для того же
адреса и модели восстанавливается при следующем запуске. `--context-window` и
`--max-output-tokens` переопределяют значения. Облачные лимиты не переносятся.
Обычный запуск не сохраняет адрес и модель; лимит ответа можно сохранить через настройки.
`--configure` и `--base-url`
с этим режимом не совмещаются. Песочница и правила разрешения команд действуют
как обычно: `--локал` меняет подключение модели, а не права процессов.

MiniMax должен обслуживаться через Chat Completions с поддержкой tools.
Формат описан в [официальном руководстве MiniMax](https://github.com/MiniMax-AI/MiniMax-M2.5/blob/main/docs/tool_calling_guide.md).
В llama.cpp нужен рабочий Jinja-шаблон MiniMax и парсер tool calls.
Агент передаёт определения инструментов в `tools`, сохраняет `reasoning_content`
между шагами и возвращает результаты через сообщения `role=tool`.
Для проверки запускается настоящий агент с полным набором инструментов:

```bash
python3 scripts/probe_local.py --live --address model-host.example:8080
python3 scripts/probe_local.py --live --address model-host.example:8080 --no-stream
```

Проверка создаёт временный проект, просит прочитать и исправить функцию,
запустить Python-команду и проверяет журнал инструментов, код завершения и
маркер `MINIMAX_LIVE_PASS`. Пользовательский проект и настройки не затрагиваются.
Первый запрос с полными инструкциями может долго обрабатываться на локальном
сервере до появления токенов; таймаут ожидания данных задаётся через
`--generation-timeout-seconds` (по умолчанию 600 секунд).

## Сборка в один файл и установка

Один раз подготовьте зависимости интерфейса (это явная загрузка с PyPI):

```bash
cd pycoder-source
python3 -m pip install --target vendor --only-binary=:all: -r requirements-ui.lock
```

После этого сборщик работает офлайн, на стандартной библиотеке:

```bash
cd pycoder-source
python3 build.py
```

Результат — **`dist/pycoder`**, один исполняемый Python zipapp. Его можно
скопировать на другой компьютер с Python 3.11+; исходники и pip там не нужны.
Python-интерпретатор в файл не включён. Внутри находятся модули агента, Textual и
его зависимости с лицензиями, LICENSE и NOTICE. Также включён комплект для
восстановления проекта: сборщик, тесты и fixtures, документация, вспомогательные
скрипты и lock-файл зависимостей. Настройки, токены, истории, журналы и кэши
в сборку не попадают. Сборщик запрещает нативные расширения, несовместимые с чистым zipapp.

### Распаковка для редактирования

Начиная с 0.4.1 установленный файл может восстановить проект в новый каталог:

```bash
pycoder --unpack ./pycoder-source
cd pycoder-source
python3 run.py
python3 -m tests.run_portable
python3 build.py
```

Можно вызвать `python3 dist/pycoder --unpack ./pycoder-source` без установки.
Без пути `--unpack` создаёт `pycoder-source` в текущей папке терминала.
Существующий каталог не перезаписывается: укажите новый путь.
В Windows используйте `python` вместо `python3`, если интерпретатор установлен под этим именем.

Распаковываются исходники именно Python-проекта PyCoder, включая `vendor/`;
Rust-репозиторий оригинального Codex и пользовательские данные не включаются.
Запуск интерфейса и повторная сборка не требуют pip или скачивания зависимостей.
Без изменений исходников повторная сборка даёт побайтово тот же файл.
После редактирования выполните `python3 build.py`, затем
`python3 dist/pycoder --install` для обновления установленного агента.
Обычный ZIP-архиватор тоже открывает сборку, но `--unpack` дополнительно
восстанавливает структуру проекта: зависимости переносит в `vendor/`, а
сборщик и тесты — из служебного каталога `_source/` на свои места.

Установить собранный файл как `/usr/local/bin/pycoder`:

```bash
python3 dist/pycoder --install
```

Если каталог недоступен для записи, установщик напечатает точную команду с
`sudo` и текущим Python-интерпретатором. Он не повышает права автоматически.
Можно установить в пользовательский каталог:

```bash
python3 dist/pycoder --install ~/.local/bin
```

Если выбранного каталога нет в `PATH`, установщик покажет строку для его
добавления; профили shell автоматически не меняются. Для текущего bash/zsh:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

При повторной установке команда заменяется атомарно, с сохранением старой версии
при ошибке копирования. Предыдущие настройки и сессии не затрагиваются. Установка
сама по себе не запускает мастер модели и не требует API-токена. Из установленного
файла также можно выполнить `pycoder --install ДРУГОЙ_КАТАЛОГ`.

После установки:

```bash
cd /путь/к/проекту
pycoder
```

**Без аргументов workspace — текущая папка терминала.** Каталог установки
программы не используется как рабочий проект. Параметр `-C` / `--workspace`
по-прежнему позволяет выбрать другую папку.

Дополнительно: `python3 build.py --output /путь/к/файлу` задаёт имя сборки;
`pycoder --version` показывает версию без загрузки конфигурации.

## Интерфейс и события

При запуске в терминале по умолчанию открывается Textual: многострочный редактор,
потоковые Markdown-ответы с подсветкой кода, раскрываемые блоки инструментов,
цветные diff, план и оценка заполнения контекста. Синий обозначает ввод пользователя,
зелёный — успешную работу, красный — ошибку, жёлтый — вопрос, фиолетовый — план.

- Enter отправляет сообщение, Ctrl+J добавляет строку, ↑/↓ в однострочном поле
  выбирают предыдущие запросы. Tab открывает меню действий: выбор сразу открывает окно,
  без вставки команды в редактор, чат или историю модели. Черновик сообщения сохраняется.
- Вопросы, настройка модели, восстановление истории и разрешения используют ↑/↓ и Enter.
  В вопросах модели есть вариант своего ответа; Tab переводит в поле ввода.
- Tab → «Настройки» открывает редактор лимитов: ответ, контекст, порог сжатия,
  число шагов, вывод инструментов, таймауты и повторы. Каждый параметр редактируется
  в отдельном окне; Esc возвращает к списку без изменения поля. Можно применить
  значения к сессии или сохранить в `config.json`. Настройки доступны во время
  генерации: рабочий поток применяет их между шагами, уже отправленный запрос
  не меняется. Лимит числа шагов действует со следующего хода.
- Контекст, план, процессы, сессия, разрешения, справка и результат ручного сжатия
  показываются в отдельных окнах. Служебные действия не добавляют сообщения в чат.
  «Продолжить задачу» запускает агент по существующей истории без нового сообщения.
- Esc используется только для возврата/закрытия окна и не прерывает работу.
  Если закрыть вопрос агента, он остаётся ожидающим ответа; Tab → «Ответить на вопрос
  агента» возвращает к нему. Отмена разрешения выполняется явным выбором «Отклонить».
- Ctrl+G явно останавливает задачу и очищает очередь сообщений.
  Ctrl+Q и пункт «Выход» открывают подтверждение с выбранным по умолчанию «Остаться».
  После подтверждения история сохраняется, дочерние процессы останавливаются.
- Во время работы можно набирать и отправлять следующие сообщения: они выполняются
  последовательно после текущего хода. Это очередь, а не вмешательство в текущий запрос модели.
- PageUp/PageDown и колесо мыши прокручивают переписку. Просмотр старых сообщений
  не сбрасывается к низу при поступлении нового текста.
- Текст ответов, ошибок, команд и diff выделяется мышью. Ctrl+C при выделении
  копирует его, без выделения не прерывает работу. Ctrl+V вставляет системный буфер. Правая кнопка мыши или F2 открывает
  меню: при выделении первым идёт «Копировать выделенное», иначе «Вставить». Также доступны копирование всего сообщения (включая скрытый код), последней ошибки
  и просмотр журнала. На macOS используется системный `pbcopy`, поскольку Terminal.app
  не поддерживает стандартное копирование Textual через OSC 52. На Linux для чтения/записи буфера нужны `wl-clipboard` (Wayland: `sudo apt install wl-clipboard`)
  либо `xclip`/`xsel` (X11: `sudo apt install xclip`). Для копирования без этих утилит
  используется OSC 52 терминала; для вставки — сочетание терминала Ctrl+Shift+V.
  Буфер читается только при вставке или открытии контекстного меню, не опрашивается фоном.
- В основном потоке показываются пояснения модели по мере поступления. Блоки кода
  с Markdown-ограждениями и отступами скрыты; полный ответ сохранён в истории и доступен
  через «Копировать сообщение целиком». Diff свёрнуты по умолчанию. Внутренние reasoning
  и аргументы инструментов не выводятся как ответ пользователю. Если модель не присылает
  пояснений вместе с инструментами, интерфейс показывает состояние, не выдумывая текст.
- Подписи инструментов содержат команду или файл, длинные подписи сокращены до 88 символов;
  подробности доступны при раскрытии. Команды отображаются как `• Running …` / `• Ran …` / `• Failed …`.
  Точка успешной команды зелёная, неуспешной — красная. Вывод показан
  с `└` и последними пятью экранными строками вывода. Хвост обновляется во время работы,
  независимо от ожидания `exec_command` и последующих `write_stdin`.
  Нажатие на заголовок раскрывает результат; кнопка «Полный вывод / следить…» открывает
  отдельный просмотр с прокруткой, страницами и слежением за хвостом. Esc закрывает
  просмотр без отмены задачи. Файлы stdout/stderr сохраняются без усечения в
  `<state>/tool-output/<session>/` с правами 0600; они занимают место на диске,
  автоматической очистки нет. Ограничение вывода для модели остаётся отдельным.
  Для файловых инструментов сохраняется весь запрошенный диапазон, а не весь файл.
  Рядом с контекстом отображается средняя скорость
  текущего запроса модели: выходные токены / время с начала запроса, включая ожидание
  первого токена. Во время потока и без usage провайдера это оценка UTF-8 байты / 4,
  обозначенная `≈`; после ответа используется `completion_tokens`, если он пришёл.
  Счётчик учитывает также генерацию аргументов инструментов и reasoning, не показывая их текст.
- Рядом со скоростью показано суммарное время запросов модели в текущем ходе
  (`модель ММ:СС`), включая ожидание, повторы и сжатие. Таймер движется даже без
  входящих токенов и останавливается при завершении/ошибке. План поддерживает
  до трёх уровней: сложные пункты можно разбить на `children` с отдельными статусами.
  Инструкции требуют вызывать `update_plan` после завершения каждого пункта/подпункта,
  перед началом следующего; откладывать обновления до конца нескольких этапов нельзя.
  Родитель и его последний подпункт могут завершаться вместе.
- Перед завершением хода агент проверяет весь план, включая вложенные пункты.
  Если остались открытые, он один раз просит модель сверить статусы с результатами
  инструментов. Если пункты всё ещё открыты, выводит предупреждение и сохраняет
  их статус: заблокированная работа не превращается автоматически в «выполнено».
  Без плана или при полностью закрытом плане дополнительного запроса нет.
  Определение границ смысловых этапов остаётся обязанностью модели; успешный патч
  сам по себе не закрывает пункт плана.
- После каждого хода (также при ошибке или отмене) показываются общее время обработки,
  входные/выходные и суммарные токены, число запросов. Время включает инструменты,
  повторы и ожидание пользователя; токены суммируются по всем запросам, включая
  сжатие. При наличии используется `usage` сервера, иначе — оценка с `≈`.
  Расход при оборванном запросе может быть неизвестен: это отмечается в итоге.
  Это счётчик обработанных токенов, а не расчёт стоимости или cache billing.
- `--plain` включает простой текстовый режим. Задача аргументом и перенаправление
  stdout сохраняют обычный CLI, удобный для скриптов.

`runtime.py` владеет агентом, историей и процессами в одном рабочем потоке.
`events.py` передаёт события UI и ответы на вопросы; `tui.py` только отображает их.
Отмена кооперативная: проверяется между действиями, при ожидании процесса и чтении
ответа модели; активный сокет закрывается через shutdown. Ожидание DNS/подключения
может завершиться только по системному таймауту. Блокировка проекта удерживается
до завершения рабочего потока.

Ошибки агента, провайдера и интерфейса записываются в `errors.log` внутри каталога
состояния (на установке с fallback это `~/.config/pycoder/state/errors.log`).
`/logs` или F3 открывает живую панель с вкладками «Поток модели» и «Ошибки».
«Поток модели» показывает текст ответа основного агента, переданный провайдером
`reasoning_content` и фрагменты имён/аргументов инструментов ещё до выполнения.
Счётчик символов и время с последнего фрагмента помогают отличить поступление
данных от ожидания. Скорость генерации учитывает эти каналы, поэтому может
меняться даже при пустом чате. Без streaming вывод появляется только после
получения ответа целиком. Если провайдер не передаёт reasoning, показать его нельзя.
Вкладка хранит последние 120 000 символов в памяти до закрытия приложения,
включая незавершённые попытки; на диск этот поток отдельно не записывается.
Во вкладке «Ошибки» новые записи появляются сами, основной диалог ими не заполняется.
Esc внутри панели, F3 или кнопка закрывают
только просмотр; агент продолжает работу. Кнопка «Открыть отдельный терминал»
запускает независимый просмотр (на macOS — Terminal.app). Также можно вручную
открыть другой терминал и выполнить `pycoder --logs`: конфигурация модели и
блокировка проекта не запрашиваются, Ctrl+C завершает только просмотр.
Файл создаётся с правами 0600 и ротируется после
1 MiB; traceback не содержит дампов локальных переменных, текущий API-токен скрывается.
История версии 0.3.0 не содержала таких диагностик: прежнюю ошибку интерфейса из неё
восстановить невозможно. Журнал локальный и никуда автоматически не отправляется.

Лимит ответа берётся из положительного целочисленного `max_output_length` каталога
выбранного сервера. Если поля нет или каталог недоступен, интерактивный запуск
спрашивает число; неинтерактивному нужен `--max-output-tokens`. Лимит сохраняется
в конфигурации вместе с источником и парой endpoint/model. Старые конфиги с
прежним 4096 проходят эту проверку при следующем запуске. При смене модели/URL
старое значение не переносится молча. Явный CLI-параметр переопределяет каталог.
Для своих серверов каталог `/models` тоже проверяется; других сетевых адресов нет.

Перед запросом максимум ограничивается только оценкой свободного контекста с
запасом. Лимиты в половину/четверть окна и потолок автоповтора 32768 удалены.
По количеству полученных токенов или общему объёму SSE клиент поток не обрывает:
дочитывает данные и завершающий статус провайдера. Положительный `stop` принимается,
даже если reported usage превышает запрошенный максимум.

При `finish_reason=length` автоматического удвоения больше нет. Для текста,
reasoning-only ответа и вызовов инструментов появляется выбор:
- оставить лимит и попросить модель выполнять оставшуюся задачу небольшими фрагментами;
- ввести больший лимит и повторить запрос (если позволяет свободный контекст);
- остановиться с сохранением истории.

Увеличение действует до выхода; сервер вправе отклонить значение выше каталога.
Все инструменты обрезанного ответа отбрасываются, даже если часть выглядит готовой;
ранее выполненные действия остаются в истории. Текстовая часть без инструментов
сохраняется для продолжения по фрагментам. Без интерактивного пользователя агент
останавливается, не принимая решения самостоятельно. При обрезанной сводке контекста можно увеличить её бюджет или остановиться;
исходная история сохраняется до успешного сжатия. При другом пустом ответе
(не `length`) может повторяться без streaming. Для Chutes/E2EE повторы ограничены
настройками окна «Серверы» (F4): по умолчанию 1 на экземпляре, 10 суммарно.
Для других провайдеров временные ошибки пока повторяются без ограничения.
Задержки между повторами: 1, 2, 4, 8, затем 10 секунд.
В чате обновляется одна плашка с номером повтора и подробностями; Ctrl+G отменяет ожидание.
Параметр `retries` сохраняется для загрузки списка моделей. Оборванный
ответ отмечается в интерфейсе; повтор использует последнюю завершённую историю.
Инструменты из оборванного ответа не выполняются, ранее выполненные не запускаются повторно.

Сетевые ожидания разделены: `timeout_seconds` (120 по умолчанию) применяется к
подключению/отправке, `generation_timeout_seconds` (600) — к ожиданию заголовков
и чтению ответа модели. Это таймаут бездействия сокета, а не ограничение общей
длительности генерации. Новый параметр применяется и к старым конфигам, где он
отсутствует; можно переопределить `--generation-timeout-seconds 900`. Долгие
вызовы инструментов некоторые серверы передают после большой паузы. Вызов
исполняется только после получения и проверки полного ответа. В журнале каждой
неудачной попытки сохраняются этап, время, пауза и объём полученного SSE; тело
запроса, ключ и текст reasoning не записываются.

Для явного живого теста только выбранного провайдера (платный запрос по его тарифу):
`python3 scripts/probe_model.py --live --mode tool --tokens 8192 --functions 80`.
Тест использует синтетическую задачу, не отправляет файлы проекта, не выполняет
полученный инструмент и печатает только счётчики/времена, без текста ответа и ключа.

## Доверие к проекту

Чтение и патчи файлов внутри выбранного workspace выполняются без подтверждений,
включая создание, изменение, удаление и перенос. Проверяются разрешённые пути и
цели символических ссылок. `--read-only` по-прежнему запрещает изменения.

По умолчанию весь shell на macOS/Linux запускается без подтверждений внутри
системной песочницы, включая `find`, пайпы, составные команды и прямой argv.
Сохранённые разрешения и `--yes` не отключают её. Подробности ниже.

Если песочница явно отключена, на macOS/Linux простые системные `head`, `tail`, `cat`, `wc`, `ls`, `grep` и
`sed -n 'N,Mp'` автоматически допускаются для явно указанных файлов проекта.
Поддерживаются ограниченные опции, буквальный `echo` и цепочки через `;` / `&&`,
если проверку проходит каждая часть. Например, `head -30 app.py; echo ====; tail -20 main.py`.
Проверяются реальные пути (включая симлинки), запрещены специальные файлы вроде FIFO;
исполняемые файлы берутся из `/usr/bin` или `/bin`, аргументы заново экранируются.
Чтение с неизвестными опциями, перенаправлениями, подстановками, glob-шаблонами,
пайпами, рекурсивным grep или пользовательской оболочкой остаётся на обычной политике.
Для shell-строк автоматический допуск работает только с `/bin/sh`; прямой argv
также поддержан. На Windows и для универсального поиска используйте инструменты
`read_file`, `list_files`, `search`, которые уже не требуют подтверждений.
Это проверка конкретной команды, а не OS sandbox и не защита от другого процесса,
который меняет файловую систему одновременно с выполнением.

В Windows или при отключённой песочнице остальная shell-команда запрашивает одно из решений: разрешить один раз, разрешить до выхода,
запомнить для проекта, отклонить. Запоминается **полная строка команды вместе с cwd
и shell**, а не опасный префикс вроде `python` или `sh`. Другая команда, другой
каталог запуска или другой проект требуют отдельного решения. Изменение содержимого
скрипта не меняет строку команды: сохранённое правило разрешает и следующие версии скрипта.
Ввод в уже разрешённый процесс не вызывает повторный вопрос.

Правила хранятся в `~/.config/pycoder/permissions/<SHA256-пути-проекта>.json`
(либо выбранном `--config-dir`), вне проекта, с правами 0600. `/permissions`
показывает и удаляет запомненные правила. Это политика разрешений, не OS sandbox:
утверждённая команда имеет права пользователя и может выйти за пределы проекта.

## Песочница и сеть

**Tab → Настройки → Песочница и сеть** открывает отдельное окно. Esc возвращает
назад, не прерывая задачу. В пункте «Режим» доступны три варианта:

- **Песочница** — команды выполняются внутри системной песочницы.
- **Без песочницы · с подтверждениями** — обычные права пользователя,
  подтверждения команд и существующие запомненные разрешения.
- **Без песочницы · полный доступ без подтверждений** — после предупреждения
  агент и субагенты запускают команды без запросов разрешения, включая
  `require_escalated`, могут работать вне проекта и пользоваться всей сетью.
  Это права текущего пользователя, без автоматического получения root.
  `read_file`, `list_files`, `search` и `view_image` могут читать вне проекта;
  для изменений вне проекта агент использует shell, а `apply_patch` остаётся привязан к проекту.

Можно выбрать сеть,
добавить, изменить или удалить адреса, применить настройки к сессии или сохранить
в общий `config.json`. Полный доступ требует подтверждения предупреждения;
до «Применить» / «Применить и сохранить» выбор остаётся черновиком.
Полный доступ хранится как `full_access=true`, `sandbox_enabled=false`, `approval="auto"`.
При возврате к другим режимам `full_access` сбрасывается, `approval` становится `ask`.
`--read-only` отключает полный доступ для текущего запуска. `--yes` сам по себе
полный доступ не включает. Прокси модели не включает песочницу принудительно.
В `--plain` настройки доступны через `/settings` → «Песочница и сеть».

По умолчанию `sandbox_enabled=true`, `sandbox_network="none"`, список адресов пуст.
Настройки применяются к **новым** процессам основного агента и субагентов.
Уже работающий сервер/процесс сохраняет прежние ограничения до завершения.

Режимы сети:

- `none`: сеть команд закрыта, включая localhost.
- `allowlist`: HTTP/HTTPS через встроенный проверяющий прокси; точные записи
  `host:port`, например `pypi.org:443` и `files.pythonhosted.org:443`. Wildcard и URL
  не принимаются. Для `[::1]:8000` или `127.0.0.1:8000` нужен также переключатель
  `sandbox_localhost`; для частной LAN — `sandbox_lan`. Эти переключатели сами
  по себе не разрешают все адреса: запись host:port обязательна.
- `all`: без SOCKS — вся IP-сеть, включая localhost и LAN; при SOCKS — сеть
  через прокси, с сохранением проверок localhost/LAN.
- `direct` («Вся сеть напрямую»): вся IP-сеть без прокси и списков, включая
  localhost и LAN, TCP/UDP/DNS. Файловая песочница сохраняется.

Сетевые настройки действуют только внутри песочницы. В обоих режимах без неё
ограничений сети со стороны PyCoder нет; маршруты модели и аттестации отдельные.
Поля разрешённых хостов отображаются только в режиме «По спискам адресов».
При выборе всей сети или запрете сети они скрываются; сохранённые адреса
возвращаются при повторном выборе списков. Переключатели localhost/LAN видны
только там, где они ограничивают доступ. Без песочницы сетевые поля скрыты целиком.
На macOS полная IP-сеть разрешает также приём ICMP-ответов (`ping`, `ping6`)
и UDP-пакетов; файловые ограничения песочницы сохраняются.

Allowlist проверяет точный адрес назначения, DNS-ответы и порт, а затем подключается
к уже проверенному IP. Link-local/служебные адреса запрещены; private/loopback
требуют соответствующих переключателей. Это ограничение сетевых адресов, не URL
и не проверка содержимого TLS-туннеля. HTTP redirects не расширяют разрешения:
для нового адреса нужно отдельное разрешение. UDP, обычный SSH и программы,
игнорирующие HTTP-прокси, не получают прямого доступа в allowlist-режиме.

Модель может вызвать `request_network_access(host, justification)`: отдельное окно
предлагает отказ, доступ до выхода или сохранение адреса **в общих настройках**.
При отказе команда не повторяется. Разрешение адреса не отключает файловую защиту
и не меняет localhost/LAN-переключатели. Сам агент продолжает обращаться к выбранной
модели независимо от сетевой политики shell; API-ключи не передаются командам.

**macOS:** `/usr/bin/sandbox-exec`, генерируемый Seatbelt-профиль; базовые SBPL-правила
взяты из оригинального Codex с указанием в NOTICE. Прямая сеть закрыта; в allowlist
разрешено соединение только с локальным прокси конкретного процесса.

**Linux x86_64/aarch64:** требуется установленный Bubblewrap (`sudo apt install bubblewrap`
на Ubuntu) и доступные user namespaces. Он создаёт отдельные user/PID/IPC/UTS
пространства имён, подключает файловую систему read-only, проект, системные temp-каталоги и scratch — writable.
При закрытой/ограниченной сети используется отдельное network namespace. Allowlist
работает через TCP→Unix relay к хостовому прокси. Перед запуском команды seccomp
блокирует Unix sockets, ptrace/process_vm, pidfd_getfd и io_uring, чтобы команда
не могла обойти прокси через сокеты хоста или доверенный relay. Механизм требует
поддержки seccomp ядром; при невозможности установки фильтра команда не запускается.
Некоторые Ubuntu/AppArmor-профили запрещают user namespaces: нужна настройка хоста,
автоматически системные политики PyCoder не меняет. Отсутствующий/неработающий backend
никогда не заменяется незаметным запуском без защиты.

**Windows:** системной песочницы пока нет; действуют прежние подтверждения команд.

Файловая политика разрешает чтение ОС и программ, запись — в проект, индивидуальный
scratch, `/tmp`, `/var/tmp` и системный temp-каталог Python (на macOS это обычно
`/private/var/folders/.../T`). `/tmp` на macOS учитывается как `/private/tmp`.
`TMPDIR`, `TMP`, `TEMP` указывают на общий системный temp-каталог: файлы сохраняются
между командами, автоматически PyCoder их не удаляет. `HOME` остаётся отдельным
каталогом в scratch; окружение ограничено
PATH, локалью и терминальными переменными. Конфигурация/история агента, `.ssh`, `.aws`,
`.gnupg`, `.codex` защищены; существующие `.git`/`.agents` проекта доступны только для
чтения. Остальные файлы вне проекта могут быть доступны для чтения — это не режим
«виден только проект». Произвольные имена секретных файлов автоматически не обнаруживаются.
Unix-сокеты хоста закрыты и в режиме `all`; Docker socket и подобные интеграции
потребуют отдельного решения. Scratch удаляется после завершения команды.

Ошибка команды возвращается модели с exit_code, выводом и метаданными песочницы;
отказы прокси включают запрещённый адрес. Обычный ненулевой код не считается
доказательством блокировки песочницей. Для необходимого запуска с обычными правами:

```json
{"cmd": "команда", "sandbox_permissions": "require_escalated", "justification": "Конкретная причина"}
```

Открывается предупреждение **«Запуск вне песочницы»**, по умолчанию — отказ.
Разрешение только на один запуск, даже при `--yes` и сохранённых правилах.
Без интерактивного пользователя такой запуск отклоняется. Автоматического повтора
нет: первая попытка могла уже внести изменения. `--read-only` запрещает и эскалацию.
Песочница не отменяет повреждение файлов внутри разрешённого проекта; она также
не задаёт квоты памяти/CPU/диска и не заменяет Git или резервные копии.

## Фоновые процессы

Постоянная строка **«Фоновые процессы: N/5 · открыть»** показывает число работающих
команд основного агента и всех субагентов вместе. Она обновляется и во время
генерации ответа, и после самостоятельного завершения процесса. Нажатие открывает
список; он также доступен через **Tab → Процессы**. Для каждой команды показаны
владелец, PID, время работы, команда, рабочая папка и session_id владельца.
Кнопка «Остановить процесс» останавливает выбранную команду, не прерывая агента.

По умолчанию разрешено **5 одновременно работающих управляемых команд** во всей
команде агентов. Значение `max_background_processes` можно изменить в настройках
(1–32). Во время запуска обычная команда тоже занимает слот; это счётчик сессий
выполнения, не всех PID компьютера или дочерних процессов внутри одной команды.
Завершённая команда освобождает слот, даже если её вывод ещё не был получен через
`write_stdin`. Сохранённые результаты имеют отдельный технический предел.
Не используйте daemonize/setsid для серверов: запускайте их обычным `exec_command`
и сохраняйте выданный session_id. Песочница по-прежнему ограничивает сеть серверов.

## Запуск из исходников

Установка пакетов не нужна:

```bash
python3 run.py --workspace /путь/к/проекту
```

При первом интерактивном запуске появятся запросы:

1. **Chutes.ai или свой сервер / локальная модель.**
2. Для Chutes сразу запрашивается API-ключ (скрытый ввод), если он ещё не задан.
3. Загружается актуальный список через `GET https://llm.chutes.ai/v1/models`.
4. Выбор модели по номеру или ID. Enter выбирает **`moonshotai/Kimi-K3-TEE`**.

Размер контекста и ограничение ответа берутся из каталога, когда они указаны.
Если Kimi K3 отсутствует в текущем списке, другая модель автоматически не
подставляется: требуется явный выбор. Если загрузка каталога не удалась,
существующая конфигурация не заменяется. Для своего сервера вручную вводятся URL,
токен (или `-`), ID модели и контекст. Затем проверяется каталог этого сервера;
размер ответа запрашивается только если каталог его не сообщает.

На следующих интерактивных запусках показываются текущие модель и URL:
Enter продолжает работу, `c` открывает настройки. `--configure` запускает
только настройку. Каталог загружается при настройке, смене endpoint/model или
миграции старого лимита; готовое значение кэшируется в конфигурации. Мастер можно
открыть командой `pycoder --configure`. Значение 32768 — резервная настройка для
сервера, который не сообщил размер окна.

ID Kimi K3 указан на [странице модели Chutes](https://chutes.ai/app/chute/chutes-moonshotai-kimi-k3-tee)
и проверяется по полученному во время настройки каталогу.

Сетевой интерфейс Chutes: Chat Completions и `Authorization: Bearer …`,
согласно [официальному руководству Chutes](https://chutes.ai/agents/connect).
Реальная совместимость конкретной модели зависит от её поддержки tools/streaming.
OpenAI SDK не используется.

### Chutes: сквозное шифрование и TEE

Для Chutes PyCoder автоматически проверяет каталог моделей и пытается использовать
E2EE. Основание — поле `confidential_compute=true`, а не суффикс имени модели.
Перед отправкой текста проверяются Intel TDX/DCAP, отсутствие debug-режима,
привязка свежего nonce к ключу ML-KEM-768 и аттестация NVIDIA GPU.
Ответы, включая streaming и аргументы инструментов, расшифровываются локально.
Проверка аппаратного ключа обновляется в фоне через 5 минут, срок доверия — 8 минут; другой ключ или
сервер требуют новой проверки. Одноразовые nonce запросов не переиспользуются.

При запуске чата PyCoder проверяет библиотеки E2EE. Если они отсутствуют или
не импортируются, автоматически открывается окно установки с живым логом.
После успеха запуск чата продолжается без ручного перезапуска. При ошибке
окно остаётся открытым с подробностями. Установку также можно запустить вручную:

```bash
python3 pycoder --setup-e2ee
```

На Ubuntu для создания окружения может понадобиться пакет `python3-venv`.
Установщик предупреждает: скачивание идёт **напрямую, без прокси**, включая
случай включённого SOCKS. Прокси из окружения и настройки pip игнорируются.
Маршруты запросов модели и аттестации не меняются.
Пакеты скачиваются с PyPI в `<config-dir>/e2ee-env`, установка не требует sudo
и не меняет системный Python. После установки обычный запуск PyCoder автоматически
использует это окружение. Само приложение остаётся одним файлом; нативные библиотеки
хранятся отдельно, поскольку зависят от ОС и версии Python. При обновлении Python
повторите установку. Альтернатива для своего venv: `pip install -r requirements-e2ee.txt`.

Название модели в TUI:

- зелёное — E2EE, аппаратная аттестация Intel/NVIDIA прошла;
- голубое — проверка или подготовка шифрования;
- красное — проверка/шифрование не сработали;
- жёлтое — запрос без E2EE.

При отсутствии поддержки, библиотек или успешной аттестации запрос блокируется.
Окно предлагает остановиться, повторить проверку или явно отправить **один**
запрос без E2EE. В последнем случае остаётся HTTPS; провайдер может прочитать
запрос и ответ. Разрешение не сохраняется и не передаётся субагентам.
Сетевой обрыв допускает ограниченный повтор с новой подготовкой E2EE.
Временные ошибки получения метаданных (HTTP 429, 408, 500, 502, 503, 504 и сетевые
сбои) учитываются в общем лимите повторов, без предложения отключить E2EE.
Учитывается `Retry-After`; при 429 без этого заголовка ожидание составляет 60 секунд.
Ожидание можно отменить. После исчерпания попыток запрос останавливается.
После частичного ответа применяется выбранное действие в настройках серверов;
по умолчанию запрос останавливается, а следующий выбирает другой экземпляр.
Автоматического перехода без E2EE нет; разрешение на один запрос без E2EE не допускает повторной отправки.
В неинтерактивном режиме при отказе защиты запрос завершается ошибкой.
Эта политика действует также для сжатия контекста и запросов субагентов.
Другие провайдеры пока используют обычный транспорт с явной отметкой «без E2EE».

Аппаратная аттестация и проверка конкретного образа ПО — разные проверки.
По умолчанию доверяем развёртыванию Chutes, а строка статуса указывает
«образ ПО не закреплён». Для проверки начального измерения образа задайте
`e2ee_mrtd` в config.json: список разрешённых MRTD (по 96 строчных hex-символов),
полученных из независимо доверенного источника. Это закрепляет MRTD, но не RTMR
и не веса модели. Список не заполняется автоматически из полученной аттестации.
Локальная история PyCoder сохраняется как прежде: E2EE защищает передачу модели.
Проверка аттестации обращается к Intel PCS и NVIDIA NRAS; им передаются
доказательства оборудования, не текст запроса и не ключ Chutes.

Протокол: [Chutes TEE verification](https://github.com/chutesai/chutes-api/blob/main/docs/tee-verification.md).
Криптография: официальный пакет [chutes-e2ee](https://github.com/chutesai/chutes-e2ee-transport),
Intel-проверка — `dcap-qvl`, GPU-проверка — `nv-attestation-sdk`.

Можно передать ключ через окружение: `CHUTES_API_KEY` для `llm.chutes.ai` или
`PYCODER_API_KEY` для явно выбранного сервера. Ключ не передаётся аргументом CLI.
Введённый вручную ключ сохраняется отдельно от конфигурации с правами `0600`,
в открытом виде на диске, и привязывается к конкретному URL endpoint. Для хранения
только в окружении задайте переменную до запуска. При смене endpoint сохранённый
ключ не переиспользуется. Значение `CHUTES_API_KEY` не уходит на пользовательский
домен; `PYCODER_API_KEY` означает явное разрешение использовать ключ для текущего URL.

## Пользовательский URL и локальные модели

Поддерживается базовый URL и полный адрес `/chat/completions`:

```bash
python3 run.py -C /путь/к/проекту \
  --base-url http://127.0.0.1:1234/v1 \
  --model YOUR_MODEL_ID --no-auth
```

Можно задать собственный префикс, например `https://host.example/api/v1`.
При настройке пользовательского сервера `-` в поле токена означает отсутствие
авторизации. HTTP поддержан для локальных серверов; для удалённого используйте HTTPS.
Responses API не требуется: адаптер использует Chat Completions с JSON tools.

Одна задача без интерактивного диалога:

```bash
python3 run.py -C /путь/к/проекту --yes "Исправь ошибку и запусти связанные тесты"
```

`--yes` автоматически разрешает обычные команды в прежнем режиме без песочницы.
На macOS/Linux sandbox-команды и так не требуют вопросов; `--yes` не разрешает
эскалацию или добавление сетевых адресов. При отключённой песочнице и на Windows
неизвестные команды без интерактивного терминала отклоняются, если нет `--yes`.
`--read-only` полностью запрещает патчи и shell-команды,
оставляя чтение/поиск, планирование и диалог с моделью.

## Что перенесено

| Поведение | Реализация |

| Цикл Codex: запрос → завершённые tool calls → результаты → следующий запрос | `pycoder/agent.py` |
| Streaming текста и аргументов tools, несколько вызовов за ответ | `pycoder/transport.py` |
| История накапливается до контрольной точки сжатия | `pycoder/history.py` |
| Незавершённые вызовы после сбоя получают результат «исход неизвестен» и не запускаются заново автоматически | `pycoder/history.py` |
| Отдельный запрос на сжатие той же моделью, исходный шаблон сводки Codex | `pycoder/agent.py`, `pycoder/prompts.py` |
| Сохранение последних пользовательских сообщений + сводки, восстановление базовых инструкций | `pycoder/agent.py` |
| Оценка токенов по UTF-8 байтам / 4, дополненная usage провайдера | `pycoder/util.py`, `pycoder/agent.py` |
| Ограничение вывода инструментов с сохранением начала и конца | `pycoder/util.py` |
| Патчи Add/Update/Delete/Move, несколько фрагментов, якоря контекста и EOF | `pycoder/patch.py` |
| Поиск строк: exact → rstrip → strip → Unicode-нормализация; замены с конца файла | `pycoder/patch.py` |
| Продолжительные процессы, PTY, stdin, ожидание, тайм-аут и остановка группы процессов | `pycoder/processes.py` |
| План и статусы шагов, вопросы пользователю, разрешения | `pycoder/tools.py` |
| Инструкции `AGENTS.md` в корне и вложенных каталогах | `pycoder/tools.py` |

Для вложенных каталогов `read_file` возвращает действующие инструкции вместе
с содержимым. Если при применении патча обнаружены ещё не показанные инструкции,
инструмент сначала возвращает их модели и требует повторного вызова.
Инструкции выше выбранного workspace автоматически не загружаются. Shell остаётся
универсальным инструментом: соблюдение `AGENTS.md` при произвольных командах
опирается на инструкции модели и подтверждение пользователя.

Инструменты: `read_file`, `list_files`, `search`, `apply_patch`, `exec_command`,
`write_stdin`, `update_plan`, `request_user_input`, `get_context_remaining`.
Дополнительно: `shell` (argv), `current_time` (Codex `clock.curr_time`), `sleep`,
`new_context`, `view_image`; `list_processes` — локальное расширение для управления
сессиями процессов. `request_user_input` принимает до трёх вопросов с вариантами,
совместимыми по структуре с Codex; прежний одиночный `question` также поддерживается.
`new_context` планирует сжатие после результатов текущего набора инструментов.
`view_image` читает PNG/JPEG/GIF/WebP до 4 MiB и передаёт изображение в следующем
запросе выбранной модели; необходима поддержка изображений моделью/провайдером.
Изображения сохраняются в локальном журнале и не загружаются на внешний хостинг.
`rg` используется для поиска, если установлен; иначе работает Python-реализация.
Git, компиляторы и тестовые раннеры вызываются через shell и должны быть
установлены в рабочем окружении, если нужны задаче.

## Субагенты и параллельные инструменты

Модель может вызвать `spawn_agent`, `send_message`, `followup_task`, `wait_agent`,
`list_agents`, `interrupt_agent`, `get_agent_log` и `get_agent_result`. По умолчанию доступны три
одновременных субагента плюс основной агент. Tab → Настройки меняет `max_subagents`
(0 отключает новые запуски) и `parallel_tools` (по умолчанию 4). Новые настройки
модели наследуют следующие запускаемые агенты; уже работающие сохраняют свои параметры.

Каждый субагент использует тот же endpoint/ключ/model, отдельный Client, историю,
контекст, сжатие и отмену. `fork_turns` позволяет скопировать контекст родителя;
по умолчанию передаётся только задание. Вложенный запуск субагентов не разрешён.
Рабочая папка общая: основному агенту нужно назначать непересекающиеся файлы.
Патчи защищены общим замком и проверкой изменившегося исходного содержимого.
Это не worktree-изоляция: фоновые shell-команды всё ещё могут конфликтовать.

Основной агент получает результаты через почтовую очередь на границе шага и
перед завершением ждёт работающих агентов. Он отвечает за интеграцию и проверки.
Долгий результат можно дочитать через `get_agent_result`; сообщение о завершении
само по себе не означает успех, статус может быть `error` или `interrupted`.
`get_agent_log(target)` позволяет главному агенту проверить работу подчинённого:
фазу, время с последнего события, план, потоковый текст, последний вывод инструмента
и хвост журнала. `offset=0` читает с начала, `journal.next_offset` — продолжение;
смещения и `limit` задаются в байтах UTF-8 (по умолчанию 6000, максимум 24000).
Хвост может начинаться посередине записи JSONL. Доступ ограничен собственной командой
текущей сессии и не требует подтверждения. Читать эти журналы через shell не нужно:
папка состояния остаётся защищённой песочницей. Долгое отсутствие событий само по себе
не доказывает зависание — модель может ещё генерировать ответ.
`send_message` доставляет уточнение между шагами; `followup_task` продолжает
завершившегося/прерванного агента по его истории. В текущей сессии сохраняются
до 64 агентов; повторные задачи используют существующего через `followup_task`.

Tab → Субагенты показывает статусы, план, ответ и путь к журналу, позволяет
остановить выбранного агента. Вопросы параллельных агентов предъявляются по одному
с именем автора. Ctrl+G/выход в TUI останавливают всю команду и дожидаются освобождения
процессов перед снятием блокировки проекта. Счётчик токенов включает всех агентов.
После окончания задачи субагента его фоновые процессы останавливаются.
В `--plain` субагенты не запрашивают stdin одновременно: незапомненная команда
отклоняется (либо используйте `--yes`), вопрос возвращается основному агенту.

Независимые `read_file`, `list_files`, `search`, `current_time`,
`get_context_remaining` внутри одного ответа выполняются параллельно. Остальные
вызовы образуют последовательные границы. Результаты записываются в порядке
вызовов модели; события отображения приходят по мере готовности. Команды можно
перекрывать через существующие фоновые сессии `exec_command` / `write_stdin`.
Журналы субагентов находятся в `<state>/agents/<parent-session>/`, не перемешиваются
с основным диалогом и не возобновляют потоки автоматически после перезапуска.

## Ubuntu и Windows

Единый zipapp не требует Rust, OpenAI SDK, Bash или инструментов macOS на Windows.
Системный Python 3.11+ остаётся обязательным. `shell` теперь запускает argv напрямую;
`exec_command` использует `/bin/sh` на macOS/Linux и PowerShell (резервно cmd.exe)
на Windows. Системный промпт получает фактическую ОС, shell и путь к Python.

Ubuntu: действуют `XDG_CONFIG_HOME` / `XDG_STATE_HOME`. Буфер обмена использует
`wl-copy`, `xclip` или `xsel`, если они установлены; иначе OSC 52 терминала.
Установка: `python3 dist/pycoder --install ~/.local/bin` или системный каталог.

Windows: `python dist/pycoder --install` устанавливает `pycoder.pyz` и небольшой
`pycoder.cmd` в `%LOCALAPPDATA%\Programs\PyCoder`. Добавьте каталог в пользовательский
PATH, как подсказывает установщик. По умолчанию настройки находятся в
`%APPDATA%\pycoder`, состояние — в `%LOCALAPPDATA%\pycoder\state`; существующие
legacy-папки сохраняются. `--config-dir` / `--state-dir` действуют на всех ОС.
Права 0600 применяются на POSIX; на Windows используются унаследованные ACL профиля.

Windows использует именованный mutex для блокировки проекта/истории и Job Object
для остановки дерева процессов. Python-лаунчер не запускает команду до включения
в Job Object. Нативный буфер обмена вызывается через ctypes; без доступного
console HWND остаётся OSC 52. Реализация сверена с документацией Microsoft:
[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw),
[OpenClipboard](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard).

Справка учитывает ОС: на macOS указан ⌘C, на Ubuntu/Windows — Ctrl+Shift+C;
Ctrl+C/Ctrl+V и меню F2 работают как общие варианты; Ctrl+G останавливает задачу. Ctrl+J — перенос строки,
Esc — назад, Ctrl+Q — выход с подтверждением. Fn и перехват сочетаний конкретным
терминалом определяются клавиатурой/его настройками, а не только ОС.

CI `.github/workflows/pycoder-tests.yml` содержит Ubuntu/Windows/macOS и Python
3.11/3.14. На POSIX запускается полный набор, на Windows — переносимый набор и
нативные проверки mutex, дерева процессов, запуска argv и установки `.cmd`.
Локально: `python -m tests.run_portable` из каталога `pycoder`.

## Сжатие и ограничения

Сжатие запускается перед следующим запросом при достижении заданного порога
(по умолчанию 80% окна), но не позже 95% окна минус резерв ответа.
Запрос на сводку не содержит tools. Последние пользовательские сообщения
сохраняются с бюджетом до 20000 токенов, адаптированным к небольшим окнам.
Если запрос не помещается, из его рабочей копии удаляются старейшие целые группы
«вызовы инструментов + результаты». Исходный журнал не переписывается.
Неудачная, оборванная или не освобождающая контекст сводка не заменяет историю.

Это оценка токенов, не точный токенизатор конкретной модели. Указывайте её
фактическое окно; для неизвестного сервера оставляйте запас. Сжатие может терять
детали. Неподходящую или слишком маленькую модель код агента не компенсирует.

## Локальные данные и продолжение работы

- `~/.config/pycoder/config.json` — настройки, без токена.
- `~/.config/pycoder/credentials.json` — токен, если введён через мастер.
- `~/.local/state/pycoder/sessions/ID.jsonl` — полный локальный журнал,
  включая вывод инструментов и контрольные точки контекста. Он может содержать код.

Если стандартный каталог истории ещё не существует и его нельзя создать
(например, `~/.local/state` принадлежит root), используется резервный путь
`~/.config/pycoder/state/sessions/`. При другом `--config-dir` резервная папка
находится внутри него. Выбранный резервный путь используется и на следующих
запусках; фактический путь журнала показывается при старте. Доступность записи
проверяется до запроса ключа и загрузки моделей. Уже существующая история при
ошибке прав не скрывается переключением на новую папку. Явный `--state-dir` или
`PYCODER_STATE_DIR` также не заменяется автоматически.

Пути изменяются через `--config-dir`, `--state-dir`, `PYCODER_CONFIG_DIR`,
`PYCODER_STATE_DIR`. Файлы сессий создаются с правами `0600`.

При интерактивном запуске в знакомой папке программа находит последнюю по времени
активности сессию этой папки и спрашивает: **«Восстановить контекст прошлой сессии?»**.
Выбор «Восстановить» возвращает сообщения, результаты инструментов, план и
контрольную точку после сжатия; «Начать новую сессию» сохраняет старый журнал.
В `--plain` этот же вопрос использует `[Y/n]`.
Пустые сессии, в которых ещё не было задачи, пропускаются. Старые JSONL-журналы
распознаются без миграции. Восстановление само по себе не запускает задачу:
можно дать новое сообщение или ввести `/continue`.

`--new` создаёт новую сессию без вопроса; `--resume ID` явно выбирает старую.
В неинтерактивном режиме без `--resume` создаётся новая сессия: контекст прошлой
задачи не подмешивается без согласия пользователя.

```bash
python3 run.py --list-sessions
python3 run.py -C /тот/же/проект --resume SESSION_ID
```

Процессы не сохраняются при выходе: они останавливаются вместе с агентом.
В одной папке разрешён только один работающий экземпляр PyCoder. POSIX-блокировка
самого каталога берётся до настройки и выбора сессии; второй экземпляр получает
понятную ошибку. Символические ссылки на ту же папку и другой `--state-dir` не
обходят блокировку. При выходе или аварийном завершении ОС автоматически снимает
её; файлы блокировки не остаются. Это не блокирует сторонние редакторы и не
распространяется на другие папки. Отдельная блокировка самого журнала сохранена.

В TUI основные действия доступны через Tab. Старые slash-команды оставлены как
совместимые сокращения и открывают те же окна без сообщений в чате. В простом
текстовом режиме доступны `/help`, `/settings`, `/compact`, `/continue`, `/context`, `/plan`, `/session`,
`/processes`, `/permissions`, `/exit` (последние две панели доступны в TUI).
В текстовом режиме Ctrl+C (в TUI Ctrl+G) прерывает запрос/инструмент и останавливает дочерние процессы.
После исправления причины ошибки `/continue` продолжает по сохранённой истории.
По умолчанию за ход разрешено 100 шагов модели; `--max-steps` меняет лимит.
Три одинаковых набора действий с одинаковыми результатами останавливают цикл.

## Сетевые обращения

Клиент модели находится в `transport.py`:
**POST на настроенный endpoint модели**, включая запросы сжатия и повторы при
временных ошибках, и **GET `/v1/models` выбранного сервера при настройке или миграции лимита** с тем же Bearer-ключом (если авторизация включена).
Нет метрик, Sentry, аналитики, проверки обновлений, облачной
конфигурации, авторизации OpenAI, MCP, загрузки плагинов или фонового обнаружения
моделей. Для клиента модели HTTP redirects запрещены и переменные HTTP(S)_PROXY не используются.
TLS проверяется стандартным SSL-контекстом Python.

Без настроенного SOCKS в allowlist-режиме добавляется локальный сетевой прокси: он выполняет DNS и
соединения только для разрешённых командой адресов. В режиме all сеть команд
не ограничена. Запуск вне песочницы имеет обычные права пользователя; удаление
API-токенов из окружения не защищает credential-файлы от такого запуска.

## Отличия от полного Codex

Это самостоятельное Python-ядро, а не перенос всех 159 Rust crates.
Реализованы субагенты одного уровня и параллельные безопасные чтения; произвольные
shell-команды не изолированы друг от друга и требуют согласования задач.
Собственный TUI на Textual не является переносом Ratatui. Нет app-server/SDK
совместимости, JavaScript Code Mode, hooks, skills loader,
генерации изображений, фоновой памяти, удалённой
компактации OpenAI. Закрытая серверная логика OpenAI не воспроизводится.
Код и prompt не делают локальную модель эквивалентной моделям Codex.

По функциональности ещё отсутствуют: вложенные команды агентов, восстановление
живых субагентов после перезапуска, выбор отдельной модели для каждого агента;
загрузка MCP/плагинов/skills и lifecycle hooks; отдельный Plan mode и встроенный
review изменений; управление ветками диалога (`fork`, `side`), worktree и переключение
сессий прямо в TUI; встроенные web search, генерация изображений, голосовой режим;
интеграции IDE/Desktop через app-server. Shell может запускать git и другие утилиты,
но это не заменяет соответствующие панели и управление состоянием.
Сохранение истории и возобновление при запуске уже реализованы; автоматической
долговременной памяти между разными проектами нет. Есть собственная OS-песочница
macOS/Linux; полного соответствия политике разрешений Codex и Windows sandbox нет.

Использована LF-нормализующая ветка алгоритма патчей Codex: обновлённый файл
получает LF. Побайтовое сохранение смешанных CRLF/LF не реализовано. Намеренно
отличаются три поведения: Add/Move не перезаписывают существующий файл;
весь патч проверяется перед записью; при ошибке записи выполняется best-effort
откат уже записанных файлов. Запись каждого файла атомарна, но это не
транзакция файловой системы и не защита от враждебного параллельного процесса.

Нативные интерактивные PTY есть на macOS/Linux. На Windows `tty=true` выполняется
через pipes с явным уведомлением модели: ConPTY пока не реализован. Из этой
macOS-среды нативные Windows/Ubuntu-сеансы не проверялись; для них подготовлен CI.

На macOS `tty=true` назначает процессу управляющий терминал до входа в песочницу.
Профиль разрешает `/dev/tty`, поэтому SSH и `sshpass` могут читать пароль с
отключённым эхом; доступ к произвольным чужим PTY не добавляется. Для интерактивного
SSH используйте `exec_command(tty=true)` и `write_stdin`. `BatchMode=yes` отключает
парольные запросы и не подходит для такого входа. Системная папка `~/.ssh`
остаётся защищённой; ключи и known_hosts внутри проекта задаются явно.

```bash

```

## SOCKS-прокси

До первого сетевого запроса настройте прокси командой
`python3.11 ./pycoder --configure-proxy` (в установленной версии:
`pycoder --configure-proxy`). Команда сохраняет настройки и выходит.
В интерфейсе: **Настройки → SOCKS-прокси и DNS**. Изменения применяются
после перезапуска: существующие соединения и фоновые процессы не переключаются
на другой маршрут посреди работы. Настройки прокси хранятся в приватном `proxy.json` рядом с `config.json` и имеют приоритет над его полями прокси.

Поддерживаются SOCKS5 без авторизации и с логином/паролем, SOCKS4 без
авторизации и с USERID. Пароль протокол SOCKS4 не поддерживает. Для удалённого
DNS SOCKS4-сервер должен поддерживать SOCKS4a. Адрес самого прокси задаётся IP,
чтобы не выполнять отдельный DNS-запрос для его поиска.

**DNS через прокси** включён по умолчанию: имя назначения передаётся SOCKS-серверу.
При выключении этого параметра системный DNS используется напрямую — это
явное исключение из маршрутизации через прокси. При удалённом DNS проверка
IP-адреса, полученного для домена, делегируется прокси: локально остаётся
проверка точного имени и порта из allowlist. Литеральные IP проверяются локально.

При активном прокси сверху выделено **ЧЕРЕЗ ПРОКСИ**, указаны версия,
адрес и режим DNS; пароль не отображается. API, каталог моделей и метаданные
E2EE используют один SOCKS-транспорт. Недоступность прокси и ошибки авторизации
не вызывают прямого подключения. TLS продолжает проверять сертификат сервера.

При выбранной песочнице команды на Linux/macOS запускаются внутри неё.
В режимах списков и SOCKS сеть проходит
через локальный HTTP CONNECT relay, подключённый к SOCKS; программы,
игнорирующие HTTP-прокси, блокируются. Режим `none` по-прежнему запрещает сеть,
`allowlist` использует два списка точных host:port: `sandbox_hosts` через SOCKS
и `sandbox_direct_hosts` напрямую, включая localhost/LAN. Остальные назначения
запрещены; пересечение списков недопустимо. Прямые назначения разрешаются через
relay, сырой выход из песочницы остаётся закрыт. DNS прямых адресов локальный.
`all` разрешает все назначения только через SOCKS и игнорирует списки.
`direct` явно разрешает всю сеть напрямую, сохраняя файловую изоляцию.
Эти четыре режима выбираются в настройках песочницы и действуют только для
новых команд агента и субагентов; маршруты API и аттестации не меняются.
При включённой песочнице с SOCKS в режимах `none`, `allowlist`, `all` запуск
команд вне изоляции запрещён. Если изоляция недоступна, такие команды не запускаются.
В явно выбранных режимах без песочницы команды выполняются без этой изоляции;
API через SOCKS продолжает работать независимо от режима команд.

Процесс проверки Intel/NVIDIA также изолируется и получает этот relay.
Если библиотека не поддерживает HTTP-прокси, проверка завершается ошибкой,
без обхода SOCKS и без автоматического отключения E2EE. Отдельное исключение —
установка библиотек E2EE: автоматически и через `--setup-e2ee` она выполняется
напрямую с явным предупреждением и логом. Это маршрутизация процессов PyCoder,
а не системный VPN для других приложений компьютера.

### Маршруты Chutes, Intel и NVIDIA; E2EE без аттестации

В настройках SOCKS есть независимые переключатели **Chutes / API модели**,
**Intel** и **NVIDIA**. По умолчанию все три включены, в том числе при чтении
старого `proxy.json`. Выключение переключателя означает явное разрешение
прямого соединения и локального DNS для этого сервиса. Общий переключатель
SOCKS остаётся главным. Настройки маршрутов применяются после перезапуска.

Маршрут Chutes охватывает каталог, список экземпляров и ключей, `evidence`,
зашифрованную генерацию и обычные API-запросы (включая другой настроенный сервер).
Маршрут Intel применяется к домену `intel.com` и его поддоменам, NVIDIA —
к `nvidia.com` и его поддоменам, только внутри процесса аппаратной проверки.
Неизвестные адреса, в том числе перенаправления на другие домены, сохраняют
общий SOCKS-маршрут. Команды агента используют собственный режим сети независимо
от трёх переключателей. При ошибке прокси автоматического перехода напрямую нет.
В заголовке отображаются выбранные маршруты.

В диалоге ошибки E2EE при включённых прокси и проверке аттестации доступен
четвёртый вариант: **Повторить аттестацию без прокси (один раз)**. Он разрешает
прямое получение каталога, ключей/nonce и `evidence` от Chutes и прямую проверку
Intel/NVIDIA для одной попытки подготовки E2EE. Отправка запроса модели сохраняет
настроенный маршрут Chutes. Этот выбор не сохраняется; обычный повтор снова
использует настройки. Результат успешной проверки может использоваться из
обычного пятиминутного кэша без новых прямых подключений.

Ошибка **«Метаданные E2EE: HTTP 403 (Chutes …)»** относится к ответу Chutes,
а не Intel. Теперь ошибка содержит сервис и путь без nonce. Прямой повтор
покрывает и подготовительное получение списка ключей, но не 403 от самого
`/e2e/invoke`: маршрут генерации меняется только настройкой Chutes. Ошибки аппаратной проверки отмечают
этап Intel TDX или NVIDIA GPU; код HTTP выводится, если библиотека его сообщает.

В основных **Настройках** появился выбор **E2EE: с проверкой аттестации / БЕЗ
проверки аттестации**. Применяется со следующего шага; кнопка сохранения
записывает `e2ee_verify_attestation` в `config.json`. Для одного запуска есть
`--e2ee-unverified`. Без проверки сохраняются шифрование запроса и проверка
целостности зашифрованного ответа, получение ключа и одноразовых nonce Chutes.
Запрос `evidence` и проверки Intel/NVIDIA пропускаются. Этот режим не требует
импорта библиотек аппаратной аттестации, но требует библиотек E2EE-криптографии.
Вверху постоянно отображается **СЕРВЕР НЕ ПРОВЕРЕН**. Это не режим отправки
без E2EE, и ошибки аттестации никогда не включают его автоматически.

Неизменность публичного ключа сама по себе не подтверждает актуальность
состояния TEE и сертификатов. Проверка запускается в фоне при открытии чата,
затем через 5 минут после каждого успеха. Результату для того же сервера,
ключа и политики MRTD доверяем до 8 минут: оставшиеся 3 минуты позволяют
обновить аттестацию без задержки генерации. При ошибке попытки продолжаются
с интервалом не менее 15 секунд (учитывается Retry-After).

После 8 минут без успеха TUI показывает вопрос, даже если чат сейчас простаивает.
Новые запросы ждут. Если проверка завершится успешно раньше ответа пользователя,
вопрос автоматически закрывается, а ожидающий запрос продолжается. Явный выбор
пользователя сохраняет приоритет. Для первичной проверки и нового ключа доверия
ещё нет: отправка ждёт сразу, вопрос появляется через 3 минуты. В консольном
режиме без TUI вопрос показывается при ожидающем запросе, чтобы не перехватывать
ввод нового сообщения. Проверка в фоне работает и во время ожидания ответа.

Фоновая проверка получает только каталог, ключи, nonce и evidence, не отправляя
пользовательский запрос. У неё отдельные HTTP-соединения и отмена; маршруты SOCKS
сохраняются. При закрытии чата проверка останавливается. Режим без проверки
аттестации не запускает фоновый процесс. «Подготовка E2EE» перед запросом включает
получение свежего одноразового nonce и шифрование, а не обязательную проверку TEE.

### Цепочка из двух SOCKS-прокси

В **Настройки → SOCKS-прокси и DNS** включите **Второй SOCKS через первый**
и задайте параметры второго сервера. Порядок фиксирован:

```text
PyCoder → первый SOCKS → второй SOCKS → целевой сервис
```

Для каждого звена независимо выбираются SOCKS4/4a или SOCKS5, порт и
авторизация: USERID для SOCKS4, логин/пароль для SOCKS5 либо без авторизации.
Адреса обоих прокси задаются IP. Первый SOCKS4 может подключаться ко второму
только по IPv4; для второго по IPv6 нужен первый SOCKS5.

Приложение открывает TCP-соединение только с первым сервером. Внутри туннеля
к первому устанавливается SOCKS-соединение со вторым. Если недоступно любое
звено или не прошла его авторизация, соединение закрывается: ни прямого
подключения ко второму/сервису, ни автоматического сокращения цепочки нет.

**DNS через последний прокси** передаёт имя целевого сервиса второму SOCKS
(при SOCKS4 требуется поддержка SOCKS4a). Если переключатель выключен, имя
разрешается локально. При выключенном втором звене используется прежний
одиночный прокси. Порядок и адреса звеньев видны сверху без данных авторизации.

Цепочка применяется ко всем маршрутам с выбранным прокси: Chutes/API,
Intel, NVIDIA и разрешённой сети команд. Явно выбранные прямые маршруты и
разовый прямой повтор аттестации обходят всю цепочку. Настройки сохраняются
в `proxy.json` и применяются после перезапуска. Старые конфигурации работают
с одним прокси; второй по умолчанию выключен. В `--configure-proxy` также
добавлен вопрос о втором сервере.

### Подробная диагностика аттестации

При ошибке показываются сервис (Intel TDX / NVIDIA GPU), точный этап и причина
с цепочкой вложенных ошибок. Для HTTP отображаются метод, URL, полученный статус
или ошибка соединения. Заголовки авторизации, тела запросов с evidence, JWT,
пароли и значения секретных параметров URL не выводятся. Публичные параметры
запросов Intel (`ca`, `fmspc`, `encoding`, `update`) сохраняются для диагностики.

Для проверок TDX выводятся конкретное поле и ожидаемое/полученное значение:
`status`, бит `DEBUG`, длины полей, хеш привязки `report_data` и разрешённые
MRTD. Для NVIDIA сохраняются ошибки HTTP, подписи/срока JWT, отсутствующего
ключа JWKS и несовпадения обязательных claims (nonce, secure boot, debug).

При тайм-ауте 90 секунд отображается последний записанный этап и начатый
запрос, если он известен. Intel использует нативный HTTP-клиент `dcap-qvl`:
его URL и HTTP-статус извлекаются из сообщения ошибки. Если библиотека
не раскрыла адрес, интерфейс сообщает об этом, сохраняя её исходную причину.
Диагностика не меняет правила принятия аттестации и не включает обход прокси.

При аварийном завершении проверяющего процесса сохраняются последний этап,
код завершения и ограниченный фрагмент stderr с удалёнными секретами.
Linux-запускатель сообщает сигнал (например, SIGABRT), вместо превращения
отрицательного кода сигнала в непонятный код 250. Песочница аттестации отдельно
разрешает внутреннюю анонимную пару Unix stream-сокетов для Tokio; создание
обычных Unix-сокетов и datagram-пар остаётся запрещённым. Песочницы команд
агента этого исключения не получают. Прямой сетевой доступ не открывается.

В журнале доступны две независимые кнопки: **Очистить поток** удаляет текст
вкладки из памяти, сохраняя работающую генерацию; новые фрагменты продолжают
появляться. **Очистить ошибки** удаляет сохранённые `errors.log` и `errors.log.1`.
После повторного открытия старые записи не возвращаются; новые ошибки
записываются как обычно. История чата при этом не меняется.


### Выбор экземпляра Chutes и повторы

Нажмите **Серверы (F4)** рядом с меню в нижней строке, либо откройте
**Настройки → Серверы модели и повторы**. Окно показывает ID экземпляров,
наличие в последнем полученном списке, использовался ли экземпляр, количество
успешных запросов, ошибок, неполных ответов и пользовательских отмен.
Активные запросы отмечаются отдельно. Выберите строку экземпляра для ручного
выбора или «Автоматически выбирать экземпляр». Уже отправленный запрос
не переключается. Недоступный закреплённый сервер вызывает остановку
с предложением обновить список или изменить выбор.

**Обновить** заново получает каталог и список E2EE-экземпляров через настроенный
маршрут Chutes, без генерации и без вмешательства в текущий запрос.
Chutes возвращает случайную выборку до пяти экземпляров, а не полный список
и не показатели загрузки. Старые экземпляры со статистикой остаются видимыми,
но помечаются как отсутствующие. Срок актуальности списка ограничен nonce;
для отправки клиент автоматически получает свежие nonce.

Галочка **Автоматически менять сервер при ошибках** относится к временным
ошибкам до получения частичного ответа. По умолчанию включена.
После исчерпания повторов на экземпляре выбирается другой доступный.
Пункт **Когда все доступные серверы дали ошибку** предлагает:
**Остановиться** (по умолчанию) или **Перебирать по кругу**.
Во втором режиме после исчерпания доступных экземпляров начинается новый круг:
сбрасываются исключения из-за недавних ошибок и лимит попыток на экземпляре
для нового круга, но общий лимит повторов и задержки сохраняются.
При пустом списке новый круг не запускается. Действия «Стоп» и «Стоп и смена»
при обрыве по-прежнему останавливают текущий запрос.
В режиме остановки исключённый экземпляр не выбирается снова в рамках
одного запроса; для следующих он исключается на 60 секунд либо до ручного выбора.

Для ответа, который уже начал приходить (включая reasoning и вызовы инструментов),
предусмотрено отдельное действие, независимо от галочки:

- **Стоп** — остановить запрос без смены выбранного сервера.
- **Стоп и смена сервера** — по умолчанию; остановиться, исключить ошибочный
  экземпляр для следующей попытки, без новой генерации.
- **Смена сервера и повтор** — сразу другой экземпляр и повтор исходного запроса.
  Это повторная генерация всего ответа, а не продолжение оборванного потока.

Лимиты считают повторы **после первой попытки**: по умолчанию
**1 повтор на одном сервере**, **10 суммарно** (не более 11 отправок).
Ноль отключает соответствующие повторы. При обрыве действие со сменой
выбирает другой сервер сразу, не расходуя повторы на прежнем.
Если другие доступные экземпляры закончились, применяется выбранное действие:
остановка или новый круг в пределах оставшегося общего лимита.
Лимит output tokens (`finish_reason=length`) сохраняет свой отдельный диалог.
Неполный ответ не попадает в историю и его инструменты не выполняются;
его текст остаётся в журнале, расход токенов учитывается за каждую попытку.
При отсутствии usage расход помечается как оценка/неизвестный.

Нажмите **Сохранить настройки**, чтобы применить действие и лимиты.
Счётчики и эти настройки сохраняются отдельно для каждой модели в
`<state_dir>/server-stats/<SHA256(model)>.json`, включая запросы субагентов.
Публичные ключи, nonce и содержимое запросов в этот файл не записываются.
Ручное закрепление экземпляра действует в текущем запуске.
Выбор и статистика экземпляров доступны только для Chutes/E2EE.
